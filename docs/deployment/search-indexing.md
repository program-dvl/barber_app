Scope: the approved public website under PRD sections 1–4 and 12/15,
[public website specification](../modules/public-website.md), ADR-024/026/065
and the current search-indexing decision. Private business/account/booking links
remain excluded. Operational repairs do not approve legal effectiveness, change
regional scope or certify Google indexing/rankings.

Forge's official Inertia SSR feature was enabled and started, including its
option to restart SSR after deployments. A subsequent homepage GET contained

the same release; use Forge's managed SSR process, rather than an untracked shell

```nginx

    access_log off;
    log_not_found off;

```

Retain the other nginx configuration. Validate through Forge's normal nginx
save/validation/reload flow. Do not change authentication, application settings,
booking routing or the complete deployment script to fix this one URL.

Verify `/robots.txt` returns **HTTP 200**, `text/plain`, the expected Allow rules
and `Sitemap: https://clipperdesk.com/sitemap.xml`. Then verify the sitemap and
public original HTML with the checker below. If validation/reload or unrelated
routes fail, restore the saved robots block through Forge and validate/reload
again; the previous 404 is the known rollback state. Do not remove `noindex`
from private pages as a recovery step.

Do not add an unmanaged static `public/robots.txt` containing stale environments
or overwrite a live generated sitemap. The application already owns these URLs.
A static sitemap may be generated by repository tooling only through its reviewed
interface; preserve the current publication rules and canonical host.

## Repeatable read-only check

From the repository root:

```sh
node scripts/check-public-seo.mjs https://clipperdesk.com
```

The command prints JSON and exits with a nonzero code when a check fails. It
writes no file unless an explicit existing output directory is supplied:

```sh
node scripts/check-public-seo.mjs https://clipperdesk.com --output /tmp/clipperdesk-public-seo.json
node --test tests/Scripts/public-seo.test.mjs
```

It checks only same-origin URLs in the sitemap's approved public route families;
query/fragment/private/off-origin URLs stop the crawl. It refuses redirects,
uses three concurrent GETs, has a 20-second request timeout and a 2 MiB response
limit, and performs no retries or mutations. It verifies sitemap structure,
robots HTTP status/declaration, each page's status/canonical/index directives,
single title/description (including duplicate text across pages), rendered
H1/main content/links and JSON-LD syntax.
This is a bounded checker for this application's generated markup, not a general
XML/HTML validator or Google's Rich Results test. Browser interaction, mobile
layout and field performance require separate evidence.

A successful crawl establishes current technical fetchability, not Google
acceptance. Preserve before/after reports with explicit timestamps. During a
deployment, rerun once the release is stable before treating the result as the
post-deployment baseline.

## Search Console follow-through

The sitemap was submitted in the authorized Search Console property on
2026-11-02. Its initial result was **Couldn't fetch**, with zero discovered pages;
ordinary, Googlebot-user-agent and gzip HTTP requests independently returned
identical valid XML with 127 URLs. The status subsequently changed to
**Success**, with **127 discovered pages**, without a sitemap change. The initial Google-origin fetch failure is not
established by those successful requests. Sitemap acceptance does not establish
indexing of all 127 pages. Avoid repeatedly resubmitting the same
unchanged sitemap or promising a fixed processing time.

After the robots repair and a stable full HTTP check:

1. Reopen the existing submitted sitemap and confirm Google's latest read,
   status and discovered URL count. Record a pending state until it changes.
2. Use URL Inspection for representative marketing and Help pages. Distinguish
   the indexed report from the live test; record crawl access, Google-selected
   canonical and rendered content. Request indexing for eligible changed/key
   pages when the console permits it; follow any quota/wait message.
3. Review Page indexing, Manual actions, Security issues and Core Web Vitals.
   Keep intentional private/noindex exclusions. Investigate unexpected
   discovered/crawled-but-not-indexed pages by their actual reasons.
4. Review Performance by page and query for impressions, clicks and position.
   An accepted sitemap or successful live test does not prove a page is indexed
   or ranking. Do not manufacture traffic, backlinks or unsupported feature copy.
5. If Google's sitemap fetch still fails, compare its latest attempt time with
   nginx/application logs and verified Google crawler access. Public user-agent
   spoof checks cannot prove access from Google's actual network.
