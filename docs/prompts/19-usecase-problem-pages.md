# Prompt 19 — Use-Case and Problem SEO Pages

Execute after Prompt 18. Build only high-intent problem/solution pages that provide practical, verified answers and a natural route into Good Hours.

## 1. Mission

Create a use-case hub and a limited set of substantive pages for real owner problems, showing precisely how existing Good Hours workflows help without promising guaranteed outcomes.

## 2. Why This Phase Exists

People often search for a problem—reducing no-shows, handling walk-ins or leaving paper—before searching for a product module. These pages should meet that intent with useful guidance and product evidence, not exist as keyword funnels.

## 3. Prerequisites

Prompts 14–18 are complete. Feature and industry route boundaries are stable. Each candidate needs a distinct search/user intent, enough helpful non-promotional content, an implemented solution path and an owner.

## 4. Read Before Changing Anything

Read mandatory docs, module specifications and requirement IDs, Prompt 14–18 IA/claims/content, operational rule evidence and relevant UI/tests. Inspect current content/blog for overlap. Treat external keyword volume as optional research, never sufficient reason to publish.

## 5. Scope

- Evaluate: reduce salon no-shows, online booking, walk-in management, staff scheduling, client management, payment management, resource scheduling, appointment reminders, switching from paper, switching from spreadsheets and switching salon software.
- Build only approved, non-overlapping problem pages plus a useful hub if warranted.
- Include diagnosis/context, practical process, how verified Good Hours features participate, constraints, next steps and related resources.

## 6. Out of Scope

Generic glossary pages, mass long-tail/city pages, competitor attack/comparison claims, promised migration services, business advice presented as professional advice, and changes to operational modules.

## 7. Product Truth

Use “help reduce” rather than “eliminate” no-shows. Explain that reminders/deposits/payment processing depend on configuration/provider state. Switching guidance must distinguish data export/import capabilities actually present. Paper/spreadsheet content must respect owners rather than shame them. No unsupported automation, AI or revenue claims.

## 8. Information Architecture

Create a candidate map with problem, search/task intent, funnel stage, unique answer, solution evidence, overlap with feature/industry/resource content, route and disposition. A page belongs here when the problem is primary; link to the feature detail for product depth and a guide for broader education.

## 9. UX Requirements

Answer the problem early, then allow readers to choose practical guidance, product workflow or evaluation. Use steps/checklists only when meaningful. State constraints near claims. Avoid aggressive interstitials and keep calls to action proportional to intent.

## 10. UI / Design Requirements

Use public primitives with editorial readability, visible callouts for practical advice/limitations, workflow diagrams and real UI proof. Do not make every page the same hero + six cards. Tables/checklists must remain semantic and useful without styling.

## 11. Content Requirements

Original copy must be actionable enough to stand without buying Good Hours. Clearly separate general operating advice from product behavior. Include definitions, realistic scenarios using synthetic data and qualifying language. Avoid fluff, arbitrary word counts, fake expert quotes, statistics without authoritative cited sources and duplicate industry-page copy.

## 12. SEO Requirements

One intent/page, unique metadata/headings and descriptive routes. Evaluate cannibalization with feature pages such as online booking and reminders; consolidate when the same answer would serve both. Use SSR, semantic steps/lists, descriptive internal links and only quality-approved sitemap entries. Do not manipulate keyword density.

## 13. GEO / AEO Requirements

Provide direct, self-contained answers to the page's question, followed by context and product-specific steps. Define terms consistently, make limitations explicit and structure related questions naturally. Citation-worthy means factual, attributable and maintained—not artificially short AI snippets.

## 14. Structured Data Requirements

Use WebPage/BreadcrumbList and, only when visible content genuinely qualifies, carefully reviewed FAQPage or HowTo eligibility. Do not use HowTo for a sales narrative, claim guaranteed results, or mark up hidden/repeated FAQs. Product references should resolve to the same Good Hours entity.

## 15. Internal Linking

Link use-case hub ↔ pages, each problem → exact supporting feature, relevant industry, pricing/trial and one or two useful resources. Link guides back where product context helps. Use varied descriptive anchors and audit for orphan/cannibalizing loops.

## 16. Conversion Requirements

Use an early low-pressure product exploration link and a later verified trial/signup CTA. Make CTA copy reflect the solved job without changing destination truth. Do not invent assessments, calculators, downloads or demo forms without full implementation and privacy ownership.

## 17. Responsive Requirements

At 360px, steps, tables, side notes, proof media and CTAs must preserve reading order and avoid overflow. Sticky navigation/CTAs are optional only when they do not obscure content. Validate tablet and desktop measures and touch targets.

## 18. Accessibility

Meet WCAG 2.2 AA; use semantic lists/steps, proper table headings, accessible callouts, visible focus, descriptive links and alt/captions. Instructions cannot rely on color, position or animation alone.

## 19. Performance Requirements

Prefer text/HTML/CSS diagrams over heavy widgets. Responsively size screenshots, reserve dimensions, lazy-load below fold and keep page bundles minimal. SSR must contain the complete useful answer.

## 20. Analytics

Use approved page topic/funnel stage/CTA placement fields. If outbound authoritative citations are tracked, exclude query/PII and respect consent. Do not use scroll depth or engagement as proof of content quality without an agreed interpretation.

## 21. Security / Privacy Considerations

Use synthetic examples; never expose customer schedules, phone numbers, health/form data or payment details. External citations must use safe links. Forms/tools are out of scope unless validated, rate-limited and covered by privacy requirements.

## 22. Implementation Instructions

1. Score and de-duplicate candidates against existing feature/industry/resource pages.
2. Produce a content brief and evidence map for each approved page.
3. Implement helpful content and verified product proof using shared components.
4. Add unique metadata, breadcrumb/link/conversion contracts and appropriate tests.
5. Review every factual/external assertion and record source/date; remove unsupported statistics.
6. Update IA, claim ledger, indexation map and status.

## 23. Do Not

- Do not publish all candidates automatically, mass-generate variants, target locations or pad copy to a word count.
- Do not shame manual workflows, name competitors without approved evidence/legal review or fabricate migration ease.
- Do not promise outcomes, guaranteed reminders/payments or Phase 2 automation.
- Do not use schema as a substitute for visible quality.

## 24. Acceptance Criteria

- Every page satisfies a distinct problem intent with useful standalone guidance and verified Good Hours support.
- Feature/industry/use-case overlap and candidate dispositions are documented.
- Published routes have unique metadata, correct schema/indexability, breadcrumbs, useful links and valid CTA destinations.
- Claims, examples and citations are accurate and maintained.
- Responsive/accessibility/SSR/tests/build pass with no thin or orphan page.

## 25. Validation / Testing

Run route/content tests, claim/citation review, duplicate-content and intent-overlap audit, heading/title/description checks, internal crawl/orphan scan, canonical/sitemap/schema validation, production SSR build, bundle/image review, mobile/tablet/desktop visual checks, accessibility/keyboard checks, console review and `git diff --check`.
