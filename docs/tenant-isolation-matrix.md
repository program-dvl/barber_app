# Tenant-isolation matrix

Status: Implemented foundation and automated evidence as of 2026-08-15.

Related requirements: FR-01, FR-05, FR-11, FR-12, FR-13, FR-19, FR-20. This matrix covers the access
and subscription foundations; every later tenant-owned aggregate must add its own row and
same-tenant, unauthorized-role, and cross-tenant test cases.

## Enforcement and evidence

| Surface | Tenant lineage and enforcement | Same-tenant evidence | Unauthorized/cross-tenant evidence | Remaining work |
| --- | --- | --- | --- | --- |
| HTTP shop routes | Canonical URLs carry `{business:public_id}`. `ResolveTenantContext` authenticates an active Membership before child binding, activates Spatie Business context, and clears it after the response. | Active assigned receptionist can read its Location. | Missing Membership is 403; a child ID from another Business is 404; an unassigned same-Business Location is 403. | Every later shop route must use the same group or an equivalent explicit resolver. |
| Model lookup and writes | Tenant models have `business_id`; public route identifiers are ULIDs; child binding uses the parent Business relationship. `BelongsToBusiness` rejects missing lineage and cross-context writes. No global scope is treated as the security boundary. | Business-scoped relationships and factories create explicit ownership. | Scoped binding and cross-context write tests deny manipulated identifiers. | Add model-specific policies and composite constraints with each aggregate. |
| Policies and roles | Spatie roles are Business-scoped and attach to Membership, not User. Policies verify active context, matching Business/User, permission, and assigned Location where applicable. | All five starter roles and custom exact permission sets are tested. | Accountant calendar access, receptionist staff management, unassigned Location, and cross-Business access are denied. | Own-calendar and own-client checks will add target StaffProfile/appointment context in scheduling/CRM prompts. |
| Invitations | Token digest, Business, role, inviter Membership, optional StaffProfile, Location assignments, expiry, revocation, acceptance identity, and timestamps are persisted. Actions repeat authorization and lineage checks inside the use case. | Correct verified email accepts once and links Membership, StaffProfile, role, and Locations. | Wrong email, foreign role/Location/Profile, expired token, revoked token, replay, and unauthorized inviter are denied. | Invitation management UI and delivery diagnostics are not yet implemented. |
| Sessions and Sanctum tokens | Membership status is checked on every tenant request. Revocation deletes all database sessions for the User, rotates the remember token, deletes matching Business/Membership tokens, and conservatively deletes legacy unscoped tokens. | Active employee request succeeds before revocation. | The same authenticated test client is denied after revocation; seeded session and token rows are removed. | Selective per-Business browser-session retention would require tenant-bound sessions; current global logout is deliberately safer. |
| Background jobs | Jobs implementing `TenantAwareJob` carry immutable `businessId` and `tenantCorrelationId`; middleware rejects missing/inactive tenants and activates system tenant context for the handler only. | Serialized payload and active-context execution are tested. | A missing/inactive Business raises instead of running without scope. | Apply the contract to every concrete later job; add retry/idempotency behavior per use case. |
| Cache and locks | `TenantCacheKey` requires a Business ID and prefixes every key with `business:{id}:`. | Deterministic tenant key is tested. | Empty identifiers/segments are rejected; distinct Business IDs cannot collide under the convention. | Later cache/lock call sites must use the helper and test invalidation. |
| Private files and attachments | A non-public `private` disk and `businesses/{id}/private/...` object-key convention are implemented. Client attachment metadata repeats Business/Client lineage; verified JPEG/PNG/PDF bytes receive hashes/classification and only hashed expiring links authorize retrieval. | Same-context upload/read and 15-minute bearer retrieval are tested. | Cross-context storage is denied; malformed/unknown/expired/revoked links fail without object-key disclosure. | Production malware-provider certification and final retention deletion remain Prompt 13/ADR-018 launch gates. |
| Exports | Export filenames include the immutable Business public ID; `exports.create` and `clients.privacy.manage` are server permissions. Client export is a Business-owned private JSON Attachment with hash, expiry, explicit sections, and omissions. | Owner/manager can complete and inspect a Client export containing profile, appointment, consent, form, attachment metadata, and an explicit financial-ledger status. | Receptionist/stylist cannot process privacy cases; exports omit internal notes/warnings, security metadata, raw tokens, and credentials. | Reporting bulk exports and the checkout-ledger section arrive with their authoritative modules. |
| Search | Search document IDs and payloads include immutable Business ID. | Document envelope construction is tested. | Cross-tenant search services must require a Business filter; no search backend exists yet. | Add adapter contract and query-level denial tests when search is introduced. |
| Platform routes and Filament | Platform roles use a separate expiring assignment table. Verified email, confirmed TOTP, and bounded platform sessions are required. A platform role does not satisfy tenant middleware. Support entry is a separate one-Business grant/session with ticket, reason, explicit scope, expiry, operator identity, and tenant banner. Legacy Filament identity/billing/catalog surfaces are deny-all. | Authorized platform roles receive only their capability matrix; an approved operator can use a granted support endpoint for its one Business. | Tenant owner, missing-TOTP or expired platform user, foreign identifier, ungranted support scope, and platform operator entering a shop route without Membership are denied. Bulk export input is rejected and alerted. | Production DB audit immutability, provider monitoring, and backup/restore evidence remain deployment gates. |
| Audit | Append-only Eloquent AuditEvent records include Business, actor User/Membership/platform role, action, target, source, correlation, time, reason, safe before/after, and redacted metadata. | Significant role, permission, invitation, revocation, and platform-role services write events. | Ordinary update/delete throws; sensitive keys are redacted. | Production DB credentials must deny ordinary UPDATE/DELETE; audit search/export UI and retention follow FR-19/OPEN-10. |
| Legacy invoice download | Existing User-owned invoice binding now has an ownership policy. | Owning User receives the PDF response. | A different authenticated User receives 403. | Retained only as legacy boilerplate; normalized Business-owned SaaS invoices use the billing route. |
| SaaS subscription and invoices | Business owns the normalized subscription, invoices, payments, changes, coupons, events, and entitlements. Tenant middleware and `billing.manage` run before Business-scoped invoice lookup. | Owner reaches its billing page and invoice/payment evidence. | Another Business owner is 403 against the foreign Business and 404 when substituting a foreign invoice under its own Business. | Live Stripe sandbox reconciliation remains a paid-launch gate. |
| Subscription webhooks | Public endpoints accept only verified provider signatures (Paddle HMAC for the active provider); events resolve Business from provider IDs or immutable Business public ID metadata. | Valid signed event updates only its mapped subscription and records invoice/payment evidence. | Invalid signature is 400; duplicate ID is a no-op; ID/payload mismatch is 409; older provider time cannot rewind state. | Production secret rotation and sandbox burst/load evidence remain. |
| Entitlement entry points | Evaluator always loads current Business subscription/plan/override state. HTTP middleware, job middleware, and import guard independently authorize stable feature/numeric keys. | Allowed trial/paid operation and export recovery are tested. | Disabled feature, excess numeric import/job use, read-only subscription write, and post-export-window access are denied. | Every concrete operational action/job/import must declare its key and increase semantics. |
| Operational calendar and appointment commands | Canonical Business routes resolve Appointment public IDs through `SchedulingRecordLookup`; policies check active Membership, Business, Location assignment, and all/own calendar permissions before versioned commands run. Booking commit now links the Appointment to a same-Business Client through the identity contract. | Owner/manager/receptionist all-calendar behavior and own-calendar policy paths use the shared command/query boundary; public, reception, and walk-in commits create/match Client context. | Accountant routes are 403; a foreign Business route is 403 and foreign child lookup cannot escape Business scope. | Later sales/messages must preserve the Appointment–Client lineage. |
| Client CRM and duplicate merge | Client, Appointment, Notes, Consent, Forms, Attachments, Privacy Requests, tags, preferred Staff/Services, and duplicate candidates repeat Business lineage with composite foreign keys. Policy checks distinguish view/contact/edit/note/sensitive/file/form/merge/privacy capabilities; own-calendar Staff are limited to Clients on their performed Appointments. | Authorized owner sees and edits one Client, records authored context, reviews candidate counts, and merges under locked current versions; sensitive-note reads leave content-free audit evidence. | Reception cannot see sensitive notes or merge/process privacy; cross-Business Client/file/preference IDs are 404/denied; spelling/contact matches never auto-merge. | Future Communication/Sale/Payment/Product foreign keys must join the merge/history/export registry when introduced. |
| Client forms and privacy | Form Requests bind exact immutable Template Versions, Client, optional Appointment, Business, due time, and a one-use hashed link. Privacy Requests bind Client/Business, type, deadline, reviewer, version, result, and optional private export. | A valid secure form link exposes only its wording and Appointment reference, submits once, and preserves exact evidence; owner/manager can process export/correction/withdrawal. | Foreign/malformed/expired/used links fail without Client enumeration; destructive anonymisation is `blocked_policy` and applies no change under ADR-018. | OPEN-02/OPEN-10 must authorize any destructive executor. |
| Communications templates/history/jobs | Settings, Templates, Intents, Messages, Attempts, Action Links, and Suppressions carry Business lineage; Client links use composite foreign keys. Settings routes require `settings.manage`; delivery jobs carry Business/correlation and activate tenant context. | An authorized owner manages and previews its templates; one event creates one message per eligible channel; Client history/export/merge preserve content-minimized evidence. Scoped platform support can inspect minimized diagnostics and replay an eligible failed message through the same idempotent service. | Foreign template preview/publish and support identifiers are denied; destination/message content is encrypted and absent from support diagnostics; invalid/inactive tenant jobs fail closed. | Provider sandbox certification remains launch work. |
| Communications provider callbacks | Public endpoints require Resend Svix or Twilio signatures. Provider IDs map back to one stored message/Business; event IDs and payload hashes deduplicate before state change. | Valid callback advances sent to delivered and records provider occurrence time. | Invalid signature is 400; event-ID payload mismatch is 409; duplicates are no-ops; older events remain ignored evidence and cannot rewind delivery. | Secret rotation and callback-burst/load evidence remain Prompt 13 gates. |
| Walk-in queue and schedule exceptions | Walk-in, block, and exception rows carry Business and Location lineage. Queue routes require `walk_ins.manage`; manager reorder/closure require `schedule.override`; selected Location access is repeated at the controller boundary. | Assigned authorized users can view/manage queue records, with every conversion committed as a same-Business Appointment; queue notification events now enter the FR-13 intent boundary. | Unauthorized role and cross-Business identifiers are denied; a failed future-capacity conversion leaves the queue entry unlinked; WhatsApp is suppressed without explicit channel opt-in evidence. | Walk-in intake should expose the approved opt-in wording before WhatsApp queue delivery is enabled. |
| Public booking flows and catalog | Booking slug resolves one active published Business. Every Location, Service, Staff, Flow, Hold, and Appointment lookup repeats that Business lineage; catalog responses omit private Staff contact/schedule data. | A valid anonymous flow can search, Hold, confirm, replay, and view its own resulting reference. | A flow secret from one Business combined with another slug/child ID is 404/422; malformed identifiers and private Staff fields are not exposed. | Provider-backed deposit coordination arrives with Prompt 10. |
| Secure Appointment self-service | Tokens are random, SHA-256 stored, purpose-bound, expiring, and Appointment/Business scoped. References are display-only. Mutations use versioned lifecycle commands and revoke older links. Communications reconstruct temporary signed bridge URLs from revocable action records rather than persisting raw bearer tokens. | A valid purpose token can view or perform only its named action and receives a fresh view link afterward. | Wrong-purpose, expired, revoked, used action, malformed, and unknown tokens fail without reference lookup or tenant enumeration. | External sender certification remains a Prompt 13 gate. |
| Public waitlist | Request, Match, Appointment opening, Location, Service, Staff, and batch all carry Business lineage. Secure join/leave additionally binds the request to its originating Appointment; the selected email/WhatsApp method becomes the intent recipient under the same Business. | Exact preferences create one active request; a matched batch can award one opening through the shared commit boundary and one opening event converges on one channel message. | Foreign child IDs are denied; active duplicates converge; a shared mobile number cannot manage another Appointment's request; deterministic batch locks make parallel sibling claims produce one Appointment. | Provider-certified offer delivery remains a launch-hardening gate. |
| Legacy billing admin | User/Cashier, Lemon Squeezy, Stripe order/subscription, product/price, and generic invoice Filament resources use a deny-all quarantine trait and do not register navigation. Package and application webhook routes/listeners are disabled. | N/A: these are deliberately non-production paths. | Direct resource access authorization is false even for platform operators. | Remove packages/tables/resources only after a data/backfill audit. |

## Required test pattern for later modules

For every tenant-owned route, action, job, export, attachment, search document,
admin tool, and cache/lock key, add fixtures for two Businesses with visibly
different ownership and prove:

1. an active same-Business actor with the required role/location succeeds;
2. an active same-Business actor without the permission or Location is denied;
3. changing only the Business or child identifier never returns or mutates the
   other Business record;
4. inactive, suspended, or revoked access is denied on the next interaction;
5. platform role alone does not enter tenant context; and
6. the significant success or denial/override event is audited where FR-19
   requires it.
